Research on system survivability · explained clearly

What remains possible after a failure?

When a complex system loses part of its hardware, its mission is not necessarily over. The harder questions are what it can still do, which information is trustworthy, and whether a change in its behaviour is safe.

Real-world case · Apollo 13 · 1970

When the equipment failed, the objective — and the way to reach it — changed.

After the Apollo 13 accident, landing on the Moon was no longer possible. The lunar module, designed for a different purpose, became a temporary life-support system for the crew. Resources were limited, so less important functions were set aside to protect the overriding priority: bringing people home.

This is a historical case of resource reassignment, not evidence validating our algorithm. It illustrates the question at the heart of the dissertation: how do we determine what is still possible, and how do we choose a safe way forward?

The idea in one minute

Four questions instead of “does it work?”

Imagine an autonomous robot losing a drive. That does not automatically make it safe to keep moving, nor does it necessarily erase every remaining capability. The answer requires a sequence of checks.

  1. 01

    What was lost?

    Identify failed or weakened resources: drives, sensors, power and computing.

  2. 02

    What can still be trusted?

    Check not only hardware but also the models and estimates driving decisions.

  3. 03

    What is still allowed?

    Reject options that are physically impossible or violate safety requirements.

  4. 04

    What should happen next?

    Choose not only the next operating mode but an admissible sequence of changes with timing limits.

The robot is an explanatory example, not a result from a separate experiment.

From intuition to research

We can now quantify this idea.

The dissertation defines a quantitative survivability measure, S(t). It summarizes how much mission-relevant functional capability the system retains in its current configuration, considering both which functions are enabled and the condition of the resources supporting them.

Mathematical model: dissertation §2.6. Model validity: §2.7. Admissible transitions: §2.8. Trajectory planning: §3.6.

S(t) ∈ [0, 1]

This is a normalized capability measure within a defined model — not the probability that the system will survive.

S is survivability in the model; t is the current time; 0 means no assessed functional capability remains; 1 is the maximum under the model assumptions.

Seven parts of the framework — from the first question to a decision

This is where deeper reading begins. Each part has its own page; their order follows the dissertation, and the technical details can be explored step by step.

01

After a failure, the system is no longer nominal.

The nominal object P0 becomes Pd after damage. From that point, control and reconfiguration must rely on the real degraded object, not on the design-time idealization.

Open module →02

The four-level hierarchy: resource → service → function → mission.

At the core is a constructive link between resources, services, functions and mission. That is what turns survivability into a computable quantity S(t).

Open module →03

Capability and admissibility are not the same thing.

The framework separates configuration structure Φ(cfg), its nominal ceiling S̄(cfg), and the current survivability S(t). A correct supervisor decision requires all three.

Open module →04

Model validity is a resource, too.

The framework introduces epistemic resources: models, estimators, identifiers and learned policies whose validity must be monitored just like the physical state.

Open module →05

Reconfigurations form a transformation space, not a list of reactions.

Each admissible configuration is a graph vertex, and each allowed transition is an edge. Reconfiguration thus becomes motion over an evolution graph.

Open module →06

Timing constraints are independent: task, reaction, sequence.

The framework must pass three independent timing checks: local task deadlines, the end-to-end response budget, and the minimum dwell time between reconfigurations.

Open module →07

The planner must choose a trajectory, not only the next node.

If the chosen configuration must remain admissible over the whole dwell interval, the problem changes from a one-step choice to selecting an evolution policy.
